# Fix: Review residue from feature 011

**Type:** Fix
**Branch:** fix/review-residue
**Status:** verified

## Goal

Clear the findings feature 011 shipped with. One is a real secret disclosure in
the test harness; the rest are an unguarded invariant, dead code, two
documentation claims the code does not keep, and a failure message that names a
file the user has never seen.

Nothing here changes what the background-jobs feature does. It is the tail of
its own review.

## In scope

- **F-73 [P2]** `tests/conftest.py` renders the whole `Settings` object into the
  assertion message when the provider pin fires, printing `JWT_SECRET` and every
  API key verbatim. Reproduced by the reviewer against a live `.env`.
- **F-74 [P3]** The `ge=` bounds and the "task deadline expires strictly before
  arq's" invariant are asserted nowhere; deleting `ge=2` leaves 134 tests green.
- **F-75 [P3]** Dead code: an unused `Path` import, an unused
  `DocumentProcessingError` import, seven unreferenced schema classes, a
  `setdefault` that should be an assignment, and `engine.dispose()` sitting after
  five deletes in one `finally` in two test files.
- **F-76 [P3]** `AGENTS.md` claims "FAILED is always written ... a document never
  goes quiet", which two paths break, and discloses the upload-retention trade
  without saying nothing ever sweeps the kept files.
- **F-77 [P3]** The stored failure reason names the generated hex filename, not
  the one the user uploaded, and a test only appears to prove otherwise because
  its fixture happens to name the file `notes.txt`.
- The real-worker Redis probe is function-scoped, costing about twelve seconds
  per test when Redis is absent.

## Out of scope

- Making the secret settings `SecretStr`. That would fix this class of leak
  everywhere rather than at one call site, but it changes every read of six
  settings across the app for one assertion that can be fixed in one line.
  Recorded as a follow-up, not smuggled in here.
- Changing what an empty document does. See the decision below.

## Decisions

Two findings asked for a judgement rather than a repair.

**`EmptyDocumentError` (F-75 item 4).** It sits in the user-facing allowlist and
nothing raises it, so the entry can never match. The reviewer noted the reason:
a PDF with no extractable text reaches `READY` with zero chunks. Raising it
would be the better product behaviour, but `test_process_handles_empty_document`
asserts the current behaviour deliberately, and changing what `READY` means is a
product decision belonging to the RAG work, not to a residue cleanup. So the
dead allowlist entry goes, the behaviour stays, and the silent success is
recorded as its own finding for a later work item rather than quietly changed
here.

**The failure message (F-77).** Fixed rather than papered over. The parser only
knows the stored path, which is a generated hex name, so it stops naming files
at all; the service composes the message with `KnowledgeDocument.filename`,
which is the name the user actually sent. This also makes the misleading
assertion true in production instead of only under its fixture.

### review-residue/F-87 [P3] closed - The per-character filter makes a large filename the most expensive thing in the upload request

**File:** app/api/routes/document.py:69
**Found:** 2026-09-21 by /audit independent current (scope: current; lens: performance)
**Why it matters:** The generator expression that drops non-printable characters is a Python-level loop over the whole name, and it runs on the event loop in an `async def` handler before the body is read and before `MAX_UPLOAD_BYTES` applies to anything. Starlette's 1 MB part limit bounds the body, not the part header: a 300,004-character filename parses through `MultiPartParser` unchanged, verified directly against python-multipart 0.0.22. Measured on this machine, the comprehension costs 23 ms at 100 KB and 191 ms at 1 MB, against 4.8 ms for the `Path(...).suffix` call the delta replaced -- so an authenticated caller can stall the single-threaded loop for roughly a fifth of a second per request with a body of a few bytes. Not a break, and authentication bounds who can do it, but it is a new cost this delta added at the one place that handles untrusted input.
**Suggested fix:** One line, before the filter: `name = name[: _MAX_FILENAME * 4]`. The result is capped at 120 characters anyway, and the multiplier leaves room for characters the filter will drop.
**Resolution:** Fixed 2026-09-21. The raw filename is bounded before any scanning, from the end rather than the start, because the basename and the extension are both at the tail. Bounding it after `basename` would not have helped: with the per-character filter removed the scan itself was the remaining cost. Independent review round 7, 2026-09-21: **closed.** The tail slice is safe and the measurement holds. A separator cannot be smuggled either, because the slice runs before `ntpath.basename`, and any tail fragment of an over-long final segment contains no separator by construction. Measured here: 1.1 ms for a 100 KB name, 2.0 ms for 1 MB and 1.2 ms for 10 MB, against the 191 ms the finding recorded.
